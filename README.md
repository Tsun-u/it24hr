# IT24hr

軟體工程師的一天。**[直接開始玩](https://tsun-u.github.io/it24hr/)**，瀏覽器打開就能玩，不用安裝。

靈感來自 [fab24hr](https://fab24hr.com/)。

## 宗旨

每個人都遞給你被標記為「Priority」的工作，因此沒有任何一件事能被真正優先處理。

這個遊戲讓玩家在一張逃不開的辦公桌前過一天，下班時用一種資料結構告訴他，他今天是怎麼排的。

厭世之餘，也讓玩家看見每個崗位的辛苦和專業：SA、PM、QC、需求單位都有自己的難處。合作、互相尊重和包容，是 IT 的美德。

遊戲裡「職稱沒有差」是在演一種不太正常的職場文化；新人手冊的角色篇則把完整的編制列出來，讓玩家知道正常的分工長什麼樣。希望台灣的職場在從小企業慢慢轉型的過程中，可以越來越正常。

## 開發原則

- 整個畫面就是那張桌子：第一人稱，鏡頭不動
- 沙盒：玩家做什麼都可以，時鐘不等人；結算卡是鏡子，不是分數
- 劇本是資料：卡片、提示、對話寫在劇本檔，程式只負責跑
- 零依賴單頁：純 JS，純邏輯的檔案同時給 `node --test` 跑
- 卡上的準備工作都有意義：文件越詳細，開發就越容易（見下一節）

## 工作之間的連動

前面的文件寫到的，後面的工作就帶入或預填。左邊的工作吃右邊那幾份：

- 開發計畫文件 ← 整理需求、需求討論
- 開發規格文件 ← 整理需求、需求討論、開發計畫文件
- 開發 ← 開發計畫文件、開發規格文件
- 驗收文件 ← 開發計畫文件、開發規格文件
- 測試程式 ← 驗收文件
- 開發（修改程式）、驗收文件 ← 檢閱程式碼（接手別人或 AI 做好的東西的卡：前端挑出要改的設計、後端標出要改的行，改的跟驗的就照挑出來的那些）

開發的 function 要預填，卡上得先有寫那句需求（卡上沒寫，IT 不會通靈），再加上開發計畫或開發規格其中一份有寫到。需求簡單的卡（例如老闆口頭交代的）實務上不會另外寫文件，卡片本身就是文件，所以只看卡上有沒有寫。

另外兩條：

- AI 開發時，測試程式先寫好的話，AI 會照測試程式的邏輯寫：對 AI 來說測試沒過就是紅燈，它會想辦法變綠。測試寫對它就寫對，測試寫錯它也跟著錯。
- 退回 SA 只發生在 IT 不能或不該直接聯絡需求單位的時候。退回時指出的問題如果對，SA 補好需求，視同有人幫忙做了需求討論，一樣影響開發計畫和開發規格。
  - 怡君開的卡：照分類複選哪裡不清楚（卡上的 `saChecks`，不計分）。勾對的她 60 分鐘後補進卡片內文（AI 那句換成問到的），計畫和規格照 `{ work: 'reject' }` 的 given 帶入；勾錯的她說「我問過了，我覺得你的提議不合理」；全部勾錯 20 分鐘原封不動丟回來。她問過的那段，需求討論再問，需求單位會說「這個怡君剛剛也問了」。
  - 玩家自己開的卡：只有一個理由「我先開卡了，分析麻煩你了。」，照開卡時指派給 SA 的流程走（90 分鐘後變成她整理過的版本）。

## 新人手冊（術語辭典）

- 詞條和「一段字裡哪些地方是術語」的切法在 `glossary.js`。解釋只講詞的意思，不講小關卡的正解。
- 畫面在 `handbook.js`：視窗層用 MutationObserver 自動把術語換成虛線小鈕（同一段只標第一次；按鈕、選項、程式碼、標題列不標——能點的字要照常能點），提示、會議飛字、舉手問題另外呼叫 `Handbook.mark`。點了浮出小卡，開著時鐘暫停；「多知道一點」打開新人手冊跳到那一條。
- 新人手冊有兩個入口：電腦桌面的捷徑（上班翻手冊時鐘照走）、識別證頁和選玩法頁的按鈕（整頁浮層）。

## 開發

```sh
node --test "tests/**/*.test.js"   # 純邏輯測試
```

直接用瀏覽器開 `index.html` 就能玩。
